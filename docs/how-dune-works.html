How dune works, from the CPU up

A reading guide from how a CPU runs a virtual machine up to every Linux mechanism dune leans on: KVM, Firecracker's internals, the jailer's chroot and namespaces, the loop-mounted XFS store, reflinks, memory mapped copy-on-write, diff snapshots, and the two layers of NAT behind each VM. Every claim points at the code that does it and a command you can run on midas to see it.

Chapter 1

The whole picture

dune turns one Linux box into a VM host whose VMs can be frozen and cloned in milliseconds. Three ideas carry the whole design:

  • A VM is a process. Each VM is one Firecracker process. Its guest RAM is ordinary memory in that process, and the CPU runs guest code through KVM. Everything Linux can do to a process (chroot it, change its uid, put it in a namespace or a cgroup) dune does to the VM.
  • A snapshot is three files. CPU and device state (vmstate), RAM (mem), and the disk (disk.ext4). Restoring those files in a fresh process gives you a VM that resumes mid-instruction.
  • Forking is cheap because nothing is copied. Disks are cloned by XFS reflink (shared blocks on disk), and RAM is mapped copy-on-write from the snapshot file (shared pages in the host's page cache). Each fork only pays for what it changes.
runs inside a guest host userspace host kernel storage

The code splits the same way. internal/vm (the Manager) is the orchestration: it decides what happens. internal/backend/firecracker knows how to run Firecracker. internal/netns builds networking, internal/storage owns the store, internal/store is the SQLite state, and cmd/dune-agent is the small program inside every guest.

Read the chapters in order the first time. Chapters 2 to 4 build up how a VM actually runs: what the CPU does, what KVM does, and what Firecracker does. That foundation is what makes chapters 7 to 9 (copy-on-write, snapshots, forks) make sense.

Chapter 2

How virtualization works

The problem a hypervisor solves

An operating system kernel is written as if it owns the machine. It runs in the CPU's most privileged mode (ring 0 on x86). It points the CPU at its own page tables by writing the CR3 register, turns interrupts on and off, programs timers, and drives devices by reading and writing I/O ports and memory-mapped registers. Put two kernels on one CPU and they would overwrite each other's page tables in the first microsecond.

A hypervisor's job is to let several kernels each believe they own the machine while the real control stays with the host. Every technique below is an answer to one question: what happens when the guest kernel executes an instruction that only the owner of the machine should execute?

Four answers, in historical order

ApproachHowTrade-off
EmulationInterpret or JIT-translate every guest instruction in software (QEMU's TCG mode).Runs anything, even another CPU architecture. Many times slower.
Trap and emulateRun the guest kernel with reduced privilege. Each privileged instruction faults ("traps") into the hypervisor, which emulates its effect on the guest's virtual state and continues.Native speed for ordinary code. Popek and Goldberg proved in 1974 that it works if every sensitive instruction is also privileged. On 1990s x86 that was false: POPF run without privilege silently ignores the interrupt flag instead of trapping, and SGDT reveals the real descriptor tables. A guest could never be fooled completely.
Binary translation, paravirtualizationVMware (1999) rewrote guest kernel code on the fly to replace the problem instructions. Xen (2003) modified the guest kernel to call the hypervisor directly (hypercalls) instead.Fast, but complex (VMware) or requiring a changed guest (Xen).
Hardware assistanceIntel VT-x (2005) and AMD-V (2006) added a separate guest mode in which every sensitive operation can be made to exit. Nested page tables followed around 2008.Unmodified guests at near-native speed. This is what KVM, and so Firecracker and dune, use.

Host mode and guest mode

Hardware virtualization doesn't remove the rings; it doubles them. The CPU is in either host mode (AMD) / root mode (Intel) or guest / non-root mode, and each has its own ring 0 and ring 3. The guest kernel really runs in ring 0, so it can load page tables and disable interrupts, but those actions affect only the guest's virtual state, or cause an exit if the hypervisor asked for one.

On AMD the hypervisor describes a guest with a VMCB (virtual machine control block): a page holding the guest's register state plus intercept bits that say which events must leave guest mode. It executes VMRUN; the CPU saves the host state, loads the guest state and runs guest code. When an intercepted event happens, the CPU saves the guest state back into the VMCB, writes an exit code, and continues in the host right after VMRUN. That transition is a VM exit (#VMEXIT). Intel's equivalents are the VMCS, VMLAUNCH/VMRESUME and "VM exit".

Exits are the cost of virtualization. A round trip into KVM and back takes on the order of a microsecond; one that continues up to the VMM in userspace costs several times that. Much of the engineering in KVM, virtio and Firecracker is about avoiding exits, or keeping them inside the kernel.

Memory: two layers of page tables

The guest kernel builds normal page tables mapping its processes' virtual addresses to what it thinks are physical addresses. Those are guest-physical addresses: offsets into the RAM the VMM gave it. Before nested paging, hypervisors kept shadow page tables, a combined guest-virtual→host-physical copy updated by trapping every guest page-table write, which was slow and complicated.

Interrupts and time

A guest needs interrupts (a disk request finished, a timer fired) and a clock. The hypervisor injects virtual interrupts by setting fields in the VMCB before the next VMRUN; the guest sees them arrive as if from real hardware. Timers are emulated: when the guest programs its local APIC timer, KVM arms a host high-resolution timer and injects the interrupt when it fires. Reading the time would be expensive if every read exited, so KVM offers kvmclock, a paravirtual clock: a shared page in guest memory where KVM publishes the scaling between the CPU's timestamp counter and real time. The guest reads time with no exit at all.

Devices: emulated, paravirtual, or passed through

  • Full emulation. Pretend to be a real device, such as an Intel e1000 network card, so an unmodified driver works. Every register access is an exit, and real drivers touch registers many times per packet.
  • Paravirtual (virtio). The guest knows it is virtual and uses a device designed for it: requests sit in rings in shared memory, and one notification can cover a whole batch. This is all Firecracker offers (chapter 4).
  • Passthrough (VFIO). Hand a real PCI device to the guest, protected by the IOMMU. Native speed, but the device's state lives in hardware and can't be snapshotted.

Where KVM fits

Hypervisors are often called type 1 (runs on bare metal: Xen, ESXi) or type 2 (runs as an application on an OS: VirtualBox). KVM blurs the line. The module turns the Linux kernel itself into the hypervisor, so it runs on bare metal, but devices and configuration live in an ordinary userspace process, the VMM. The split is roughly:

KVM (kernel)VMM (userspace: Firecracker, QEMU, Cloud Hypervisor)

Nested page tables, dirty-page loggingAllocating guest RAM (an mmap)

Chapter 3

KVM: the kernel half

Three kinds of file descriptor

KVM's whole API is ioctls on three kinds of file descriptor:

  • /dev/kvm, the system handle: check the API version and capabilities, create VMs.
  • A VM fd (anon_inode:kvm-vm), one per VM: register guest memory, create the in-kernel interrupt controller and timer, attach eventfds for device notifications and interrupts, read the dirty-page log.
  • A vCPU fd (anon_inode:kvm-vcpu:N), one per virtual CPU: get and set registers, set CPUID, and run. Each vCPU fd also has a shared page, struct kvm_run, mapped into the VMM, where KVM explains why the last KVM_RUN returned.

Stripped of error handling, every KVM-based VMM does this:

kvm  = open("/dev/kvm")
vm   = ioctl(kvm, KVM_CREATE_VM)
ram  = mmap(1 GiB)                                 // ordinary process memory
ioctl(vm, KVM_SET_USER_MEMORY_REGION, {guest_phys: 0, size: 1 GiB, host_addr: ram})
ioctl(vm, KVM_CREATE_IRQCHIP)                      // in-kernel PIC, IOAPIC, local APICs
vcpu = ioctl(vm, KVM_CREATE_VCPU, 0)
ioctl(vcpu, KVM_SET_CPUID2, ...)                   // which CPU features the guest sees
// load kernel into ram, set registers, then on a dedicated thread:
for {
    ioctl(vcpu, KVM_RUN)        // CPU enters guest mode; returns on an exit KVM can't finish
    switch run.exit_reason {
    case KVM_EXIT_MMIO: emulate the device register the guest touched
    case KVM_EXIT_IO:   emulate the I/O port
    ...
    }
}

The single most important line for understanding dune is the mmap. Guest RAM is a plain memory mapping inside the VMM process. Whatever Linux can do to a mapping (back it with a file, share it copy-on-write, track which pages were written) it can do to a VM's RAM.

Where each exit goes

Most exits never reach Firecracker. KVM handles them inside the kernel and re-enters the guest; KVM_RUN only returns to userspace when the VMM has to act.

Because a vCPU is a thread, the host scheduler decides when guests run. Four VMs with two vCPUs each on midas's 16 CPUs are just eight more threads. Nothing reserves a physical core for a guest unless you pin threads yourself.

Chapter 4

Inside Firecracker

Firecracker is a VMM written in Rust by AWS for Lambda and Fargate: thousands of short-lived, untrusted VMs per host. Every design choice follows from that: boot fast, use little memory, and expose as little code to the guest as possible. QEMU emulates a whole PC (BIOS, PCI, USB, graphics, hundreds of device models). Firecracker emulates a handful of devices and nothing else.

Threads and the event loop

ThreadDoes
firecracker (main, the VMM thread)An event loop: one epoll_wait over every device's queue-notify eventfds, the tap fd, the vsock unix socket, timer fds for rate limiters, and the API channel. All virtio data processing happens here.
fc_apiServes HTTP on /run/api.sock. It only parses requests; it passes each one to the VMM thread over a channel, wakes it with an eventfd, and waits for the reply.
fc_vcpu 0, fc_vcpu 1, …The KVM_RUN loop. MMIO and port-I/O exits are handled right here by calling into the device's register code.

Each thread installs its own seccomp filter at startup, tuned to what that thread needs. The vCPU threads, which run closest to the guest, get the narrowest list.

Configuring and booting

Until InstanceStart, the API only records configuration. This is Boot in internal/backend/firecracker/firecracker.go:

PUT /machine-config     {vcpu_count, mem_size_mib, track_dirty_pages: true}
PUT /boot-source        {kernel_image_path: "/vmlinux", boot_args: "..."}
PUT /drives/rootfs      {path_on_host: "/rootfs.ext4", is_root_device: true}
PUT /network-interfaces/eth0 {host_dev_name: "tap0", guest_mac: "06:00:ac:10:00:02"}
PUT /vsock              {guest_cid: 3, uds_path: "/v.sock"}
PUT /actions            {action_type: "InstanceStart"}

Every path there is relative to the VM's chroot (chapter 5). On InstanceStart Firecracker builds the machine:

  1. Creates the KVM VM, the in-kernel interrupt controller and timer, and mmaps guest RAM. RAM is laid out from guest-physical address 0, with a hole below 4 GiB where the device registers live.
  2. Loads the kernel. vmlinux is an ELF file: Firecracker copies each loadable segment to its physical address in guest RAM. There is no BIOS and no bootloader.
  3. Writes the boot information the kernel expects: the memory map, the command line, and tables describing the CPUs, the interrupt controller and the devices (ACPI or MP tables). The guest kernel on midas carries a PVH ELF note, which lets Firecracker use the PVH boot protocol: the vCPU starts in 32-bit protected mode at the PVH entry with a pointer to a start-info structure. Kernels without the note get the Linux 64-bit boot protocol instead, entering in 64-bit mode with page tables Firecracker builds. Either way the real-mode boot of a PC is skipped entirely.
  4. Creates the devices and registers an ioeventfd and an irqfd for each virtio queue.
  5. Creates the vCPUs, sets CPUID and registers, starts a thread per vCPU and calls KVM_RUN.

That is why a VM boots in about 2 seconds, most of it spent in the guest's systemd. The kernel command line dune passes:

console=ttyS0 reboot=k panic=1 pci=off
ip=172.16.0.2::172.16.0.1:255.255.255.252::eth0:off systemd.hostname=dune-<id>

How virtio works

Each virtio-mmio device is one page of registers at a fixed guest-physical address: an identity (magic value, device type), feature bits the driver and device negotiate, the addresses and sizes of its queues, a QueueNotify register, and interrupt status. The registers are only for setup and signaling. The data itself moves through virtqueues, ring buffers that live in guest RAM and that both sides read and write directly. Firecracker can do that because guest RAM is mapped in its own address space.

One disk write, end to end

Say a process in the guest writes a file and the guest kernel flushes it to /dev/vda:

By default the block device does the write synchronously on the VMM thread (pwrite); an optional Async engine uses io_uring instead. Network traffic follows the same pattern. To transmit, the guest posts a frame and Firecracker write()s it to the tap fd. To receive, the tap fd is in the epoll set: when it's readable, Firecracker reads the frame straight into the next receive buffer the guest posted and signals the irqfd.

QEMU can hand the network data path to a kernel thread (vhost-net) to save a copy and a context switch. Firecracker deliberately keeps every byte of device processing in its own unprivileged, seccomp-confined process, trading some throughput for a smaller attack surface.

The serial console is the opposite of virtio. Every character is an out instruction to port 0x3f8, an exit all the way to the vCPU thread, which writes the byte to stdout. That is fine for a boot log and far too slow for data, which is why dune's terminals go over vsock.

Pause, snapshot, restore

Pause. The VMM thread tells each vCPU thread to stop. A thread inside KVM_RUN can't see a message, so Firecracker sets the immediate_exit flag in its kvm_run page and sends the thread a real-time signal. The signal makes KVM_RUN return with EINTR, and the thread parks until resume. The guest is frozen between two instructions.

Snapshot. With every vCPU parked, Firecracker reads the whole machine out through KVM: each vCPU's general, segment, FPU/vector and model-specific registers and its local APIC; VM-wide state such as the interrupt controllers, the timer and the kvmclock. It adds its own device state: each virtqueue's addresses and ring positions, negotiated features, and the network and vsock state. All of it is serialized into vmstate, with a format version and a checksum. Memory goes to the mem file: everything for a full snapshot, only the dirty pages for a diff (chapter 8).

CPUID and portability. A guest discovers CPU features (AVX-512, for example) at boot through CPUID, which Firecracker filters. A restored guest keeps using what it discovered, so restoring on a CPU without one of those features would crash the guest the next time it used it. Firecracker offers CPU templates that mask features down to a common baseline for mixed fleets; dune doesn't use them, so snapshots are tied to midas's CPU, as well as to the Firecracker version that wrote the vmstate.

Restore runs the build in reverse: create the KVM VM, map the memory, recreate devices from their saved state, push every register back with the matching KVM_SET_* ioctls, and resume. There are two ways to provide memory:

  • File (dune's choice): mmap the file MAP_PRIVATE, and the host page cache supplies pages on demand (chapter 7).
  • Uffd: register guest memory with userfaultfd and hand the descriptor to a separate page-server process. Every first touch of a page becomes an event that the server answers by copying a page in, for example from remote storage. This is how fleets restore snapshots without copying them locally first, and why the jailer creates /dev/userfaultfd in every jail.

After restore, Firecracker sends the guest's vsock driver a transport-reset event, because host-side connections from before the snapshot no longer exist.

Chapter 5

Isolation, and why there is a chroot

The threat model

Assume the guest is hostile. It is root inside its own kernel and can do anything there; that is fine, the guest kernel is its to break. The question is what happens if it finds a bug in Firecracker's device emulation (say, a malformed virtio descriptor that triggers a memory bug). Then the attacker is running code as the Firecracker process on the host. Every layer below exists to make that process as useless as possible to an attacker. This is defense in depth: each layer assumes the one inside it has failed.

The jailer, step by step

Firecracker ships with a companion binary, the jailer. duned runs it as root (via systemd-run, chapter 12) with these arguments, from start() in the backend:

jailer --id <vm> --exec-file /srv/dune/bin/firecracker \
       --uid 1000NN --gid 1000NN \
       --chroot-base-dir /srv/dune/store/jail \
       --netns /run/netns/dune-<vm> \
       -- --api-sock /run/api.sock --log-path /firecracker.log ...

The jailer needs root for a few privileged steps, does them, then throws root away before any guest code exists:

  1. Create /srv/dune/store/jail/firecracker/<vm>/root and copy the Firecracker binary into it.
  2. unshare(CLONE_NEWNS): get a private mount namespace, so mount changes below are invisible to the host.
  3. Bind-mount the jail directory onto itself and pivot_root into it, then unmount the old root. Unlike a plain chroot(), pivot_root leaves no path back to the host's /; it is gone from this namespace entirely.
  4. mknod the only devices Firecracker needs inside the jail: /dev/kvm, /dev/net/tun, /dev/urandom, /dev/userfaultfd, owned by the VM's uid.
  5. setns() into the VM's network namespace, which duned created beforehand (chapter 10).
  6. Close inherited file descriptors, apply resource limits, setgid/setuid to 1000NN.
  7. exec /firecracker. Firecracker installs its seccomp filters on each thread, then serves its API.

After step 7, the process is an unprivileged user in an empty filesystem. Here is everything it can see (from the package comment in firecracker.go):

/firecracker          the binary itself (copied in by the jailer)
/rootfs.ext4          this VM's private disk           uid 1000NN, 0600, reflink
/vmlinux              guest kernel (boot only)         hard link
/vmstate, /mem        snapshot files (restore only)    root, 0444, hard links
/run/api.sock         Firecracker's REST API           created by Firecracker
/v.sock               vsock bridge to the guest agent  created by Firecracker
/firecracker.log
/dev/kvm  /dev/net/tun  /dev/urandom  /dev/userfaultfd

Why a different uid for every VM

Each VM gets a network slot N (a small integer, unique among live VMs) and runs as uid/gid 100000 + N (Manager.machine in internal/vm/vm.go). Two compromised VMs therefore can't touch each other's files or signal each other's processes, even if a bug let one see the other's jail. The snapshot files hard-linked into jails are owned by root with mode 0444: a VM can read them (it has to, to restore) but never modify them, which would corrupt every sibling fork. That also covers slot reuse: a future VM that inherits a dead VM's uid still can't write to that VM's old snapshots.

The second reason for the chroot: same path, different file

Security is half the story. The other half came out of the spike (docs/spike.md): a Firecracker snapshot records the disk's path, not the disk. If VM A was snapshotted with its disk at /rootfs.ext4, every VM restored from that snapshot will open /rootfs.ext4. Without a chroot, three forks would open the same host file and corrupt it. With a chroot each fork has its own /, so the same string resolves to a different file:

On midas, with a VM running
PID=$(pgrep -n firecracker)
ps -o pid,user,cmd -p $PID              # user is 1000NN, not root
sudo ls -l /proc/$PID/root/             # the jail, as the process sees "/"
grep -E 'Uid|Gid|Seccomp|NoNewPrivs' /proc/$PID/status   # Seccomp: 2 = filter mode
sudo readlink /proc/$PID/ns/mnt /proc/1/ns/mnt   # different mount namespaces
sudo readlink /proc/$PID/ns/net /proc/1/ns/net   # different network namespaces
cat /proc/$PID/cgroup                    # 0::/dune.slice/dune-vm-<id>.scope
Chapter 6

Storage: a filesystem inside a file

midas's /srv is ext4 on LVM. ext4 can't share blocks between files, and dune needs that for instant disk clones. Instead of reformatting a partition, dune creates a 500 GB XFS filesystem inside a file and mounts it. storage.Setup does it in three commands:

truncate -s 500G /srv/dune/store.img           # sparse: allocates nothing
mkfs.xfs -q -m reflink=1 /srv/dune/store.img   # XFS with shared-extent support
mount -o loop /srv/dune/store.img /srv/dune/store

Sparse files

A file's size and the disk space it uses are separate numbers. truncate -s 500G sets the size without allocating any blocks; the unallocated ranges are holes that read back as zeros. ls -l shows the size, du shows the allocation. When XFS writes somewhere in its "disk", the loop driver writes into the file, and ext4 allocates blocks for just that range.

The problem is the reverse direction. When you delete a VM, XFS marks its blocks free in its own metadata, but the loop file's blocks stay allocated: ext4 has no idea that XFS no longer cares about them. fstrim fixes that. It asks XFS to issue discard requests for all its free space; the loop driver turns each one into fallocate(PUNCH_HOLE) on store.img, and ext4 releases the blocks. In the spike the image shrank from 1.3 GB to 251 MB after one trim. dune runs it automatically 30 seconds after the last delete, and you can trigger it with dune storage trim.

Why everything lives on the one store

Hard links and reflinks only work within a single filesystem. That is why the jails live at /srv/dune/store/jail and not in /var: the jail's disk is a reflink of a snapshot or image, and its mem/vmstate/vmlinux are hard links. Snapshots also move files out of the jail with rename(), which is only atomic and free within one filesystem.

On midas
ls -ls /srv/dune/store.img        # first column: KiB actually allocated

sudo xfs_info /srv/dune/store | grep -o 'reflink=[01]'

Chapter 7

Copy-on-write, three ways

"Copy-on-write" appears at three different levels in dune, and keeping them apart is most of understanding forks. All three share the same idea: two users share one copy until one of them writes, and then only the written piece is copied.

WhatShared objectGranularityWho copies on write
VM disksblocks on disk4 KiB filesystem blocksXFS (reflink)
VM memorypages in RAM (page cache)4 KiB pagesThe kernel's memory manager (MAP_PRIVATE)
Snapshot chainsearlier snapshots4 KiB guest pagesKVM dirty log + Firecracker diff snapshots

And one thing that is not copy-on-write: hard links. A hard link is a second name for the same inode, so a write through either name changes the one file. dune uses hard links only for files nobody may write (snapshot files, kernels), and reflinks for anything a VM writes.

1 · Disk: XFS reflinks

A file in XFS is an inode plus a list of extents: "file bytes 0 to 64 MiB live in disk blocks 1000 to 17383". A reflink copy (the FICLONE ioctl, which storage.Reflink calls; cp --reflink does the same) creates a new inode whose extent list points at the same blocks, and increments a reference count on those blocks in XFS's refcount btree. No data moves, so cloning a 2 GiB disk takes milliseconds and zero bytes.

dune reflinks in four places: image import (cp --reflink=auto, which degrades to a sparse copy when the source isn't on the store), VM create (image rootfs → jail disk), pin (jail disk → snapshots/<id>/disk.ext4), and fork (snapshot disk → new jail disk). storage.Reflink refuses to fall back to a byte copy: a silent 2 GiB copy per fork would hide a misconfigured store.

2 · Memory: MAP_PRIVATE and the page cache

When Firecracker restores a snapshot with the File memory backend, it does not read the 1 GiB mem file into RAM. It mmaps it with MAP_PRIVATE, and that mapping becomes the guest's RAM (the memslot from chapter 3). Then the Linux memory manager does the rest:

  • First read of a page: page fault. The kernel finds the file's page in the page cache (reading it from disk once if needed) and maps it into the process read-only, even though the mapping is writable.
  • Second VM reading the same page: it's already in the page cache. Both processes now map the same physical page. One copy in RAM, two VMs.
  • First write to a page: write fault on the read-only mapping. Because the mapping is private, the kernel allocates a fresh anonymous page, copies the 4 KiB, and maps the copy writable into this process only. The file and the other VMs never see the write.

This is why the backend hard-links mem into each jail instead of reflinking it: the page cache is per inode. Two reflinked copies are two inodes and would be cached twice; one inode with several names is cached once. And because the file is never written, there's nothing for a hard link to get wrong. The comment in Restore says exactly this.

How a guest touches memory: when the guest reads guest-physical address X for the first time, the nested page table has no entry, so the CPU exits to KVM. KVM looks up X in the memslot, finds the host-virtual address in Firecracker's mapping, and faults that address in like any other process memory, which triggers the page-cache logic above. After that the hardware handles accesses to that page with no host involvement.

A side effect you will see in dune's memory meter: cgroup v2 charges a page-cache page to the cgroup that first faulted it in. The first fork to touch a shared page "pays" for it; siblings get it free. When that VM's scope is removed, the charge moves up to dune.slice. That is why hoststats sums the live VMs' scopes instead of reading the slice total.

3 · Snapshots: dirty-page tracking

The third kind is about snapshots rather than running VMs: a diff snapshot stores only the pages the guest changed since the previous snapshot. That needs its own chapter.

Chapter 8

Snapshots: what dune pin does

What is in a snapshot

FileContentsWritten by
vmstatevCPU registers, KVM state (interrupt controller, timers, kvmclock), virtio device state (queue positions), device configuration (including the /rootfs.ext4 path)Firecracker
memGuest RAM: all of it (full) or only changed pages (diff)Firecracker

RAM contains the guest kernel's page cache, including file writes the guest hasn't flushed to its disk yet. That is fine because memory and disk are captured together while the VM is paused: on restore the guest's cache and its disk agree exactly. A disk copy alone would be like pulling the power cord, but paired with its memory it is perfectly consistent.

The pin sequence

From Manager.Pin and Backend.Snapshot:

  1. Pick the kind: diff if the VM has a head (its most recent snapshot), otherwise full. Insert a DB row.
  2. PATCH /vm {"state":"Paused"}. The vCPU threads leave KVM_RUN; the guest is frozen mid-instruction.
  3. PUT /snapshot/create {"snapshot_type":"Full"|"Diff", "snapshot_path":"/snap.vmstate", "mem_file_path":"/snap.mem"}. Firecracker can only write inside its jail, so it writes there.
  4. Reflink jail/…/root/rootfs.ext4 to snapshots/<id>/disk.ext4. The guest is paused, so the disk is quiescent.
  5. rename() the two new files from the jail into snapshots/<id>/. Same filesystem, so this is instant.
  6. chown root:root and chmod 0444 all three: they are about to be shared with other VMs.
  7. Resume (if it was running) and set the VM's head to the new snapshot.

Measured on midas for a 1 GiB VM: a full pin pauses the VM for about 400 ms (writing 1 GiB), a diff pin about 50 ms.

How a diff knows what changed

Every VM is created with track_dirty_pages: true. Firecracker then registers guest memory with KVM's dirty logging flag. KVM write-protects every guest page in the nested page tables; the first write to each page causes a quick exit in which KVM sets that page's bit in a bitmap and makes the page writable again. Firecracker adds its own bitmap for pages that its device emulation wrote (for example, network packets copied into guest RAM).

A diff snapshot fetches the bitmap (KVM_GET_DIRTY_LOG, which also resets it) and writes only the marked pages, each at its own offset in mem. Clean pages are left as holes, so the file is sparse: 1 GiB apparent size, but only the changed pages allocated. In the spike, a diff with 200 MB changed took 208 MB on disk.

The bitmap is reset at every snapshot attempt. If a pin fails halfway, the bitmap may already be cleared, and a later diff on the old head would silently miss pages. So Pin clears the VM's head on failure, forcing the next pin to be full.

The rules for deleting snapshots

store.DeleteSnapshot refuses while a snapshot has children (a diff's memory is meaningless without its parent) or while it is some VM's head (that VM's next diff will build on it). Running VMs are never affected by deletes: their jails hold their own hard links and reflinks, which keep the data alive until the VM is deleted too. Snapshots are tied to the Firecracker version and the host CPU model; they don't move between machines.

Chapter 9

Forks: what dune fork SNAP -n 3 does

From Manager.Fork and Backend.Restore, for each of the N forks:

  1. Resolve the chain (store.Chain) and get a full memory file (fullMemory, chapter 8). Done once for all forks.
  2. Insert a VM row. The DB allocates a free network slot N, which fixes the uid (100000+N) and the host-side addresses. origin and head are both set to the snapshot.
  3. Build the network namespace dune-<id> (chapter 10).
  4. Create the jail directory, owned by the new uid.
  5. Reflink snapshots/<s>/disk.ext4 into the jail as rootfs.ext4; chown it to the uid, mode 0600. (The source is root-owned 0444, so the copy's owner and mode must be set explicitly; an early bug was exactly this.)
  6. Hard-link vmstate and mem (or mem.full) into the jail.
  7. Launch the jailer as in chapter 5, wait for /run/api.sock.
  8. PUT /snapshot/load {snapshot_path: "/vmstate", mem_backend: {File, "/mem"}, track_dirty_pages: true, resume_vm: true, clock_realtime: true}. Firecracker maps the memory, restores device and vCPU state, and resumes. The guest continues from the exact instruction where its parent was paused.
  9. Fixup through the guest agent (below).

Three forks of a 1 GiB VM take about 210 ms in total on midas. Almost all of that is process startup and the API calls; no data is copied.

What every fork shares, on purpose

Inside its memory each fork believes it is the original VM. That includes its IP address, its MAC address, its gateway's MAC in the ARP cache, its open file descriptors, its disk path and its vsock CID. dune doesn't try to change these. Instead it makes sure each fork's surroundings look identical: the same path in the chroot, the same addresses in its own network namespace. Chapter 10 shows how.

Some state can't be faked from outside, and is fixed from inside the guest by Manager.fixup, which calls the agent's /fixup endpoint:

Things the fixup does not change: /etc/machine-id, SSH host keys, and any TCP connection that was open in the parent (the peer will reset it, since the fork has a different NAT address on the outside). If a workload cares about those, it needs its own post-fork hook.

A fork's head starts at its origin snapshot because KVM's dirty bitmap starts empty at restore: the first diff a fork takes contains exactly what changed since that snapshot.

Chapter 10

Networking with Linux primitives

The problem

Every fork wakes up believing it is 172.16.0.2, with gateway 172.16.0.1 at MAC 06:00:ac:10:00:01. Those facts live in guest memory and can't be changed from outside. Ten forks with the same IP on one network would be chaos. The solution: give each VM a private copy of the whole network, identical inside, and translate addresses on the way out.

The building blocks

network namespace
A separate copy of the kernel's network stack: its own interfaces, addresses, routes, iptables rules and sysctls. Two namespaces can both have 172.16.0.1 without conflict. ip netns add dune-<id> creates one and pins it at /run/netns/dune-<id>.
tap device
A virtual Ethernet interface whose "wire" is a file descriptor. Firecracker opens /dev/net/tun, attaches to tap0, and reads and writes whole Ethernet frames: frames the guest sends on its virtio-net eth0 come out of tap0 in the namespace, and vice versa.
veth pair
Two virtual interfaces joined by a virtual cable. Put one end in a namespace and the other in the host, and packets cross between them.
NAT (MASQUERADE)
An iptables rule that rewrites a packet's source address to the outgoing interface's address. conntrack remembers each translation so replies are rewritten back.
ip_forward
The sysctl that lets a namespace route packets between its interfaces instead of only accepting packets addressed to itself.

A packet's round trip

The guest in slot 1 runs curl 1.1.1.1:

  1. The guest kernel routes via its default gateway 172.16.0.1, resolves its MAC from the ARP cache, and hands the frame to virtio-net. Firecracker's VMM thread pulls it from the virtio queue and write()s it to the tap file descriptor. It appears on tap0: 172.16.0.2 → 1.1.1.1.
  2. In the namespace, the kernel routes it to veth0 (default route via 10.200.0.5). On the way out, NAT #1 rewrites the source: 10.200.0.6 → 1.1.1.1. conntrack records the mapping.
  3. The packet crosses the veth into the host as arriving on dune-9e70. The host forwards it: DUNE-FORWARD accepts traffic coming in from dune+ interfaces, but drops traffic between two of them, so VMs can't reach each other.
  4. Leaving the uplink, NAT #2 rewrites the source again, to the host's own address. The internet sees midas.
  5. The reply comes back to midas. Host conntrack undoes NAT #2 (destination becomes 10.200.0.6), the ESTABLISHED rule lets it through to dune-9e70, namespace conntrack undoes NAT #1 (destination 172.16.0.2), and Firecracker reads the frame from tap0 into the guest's virtio queue.

Details that matter

  • The fixed tap MAC. The guest's ARP cache, in its memory, maps 172.16.0.1 to whatever MAC tap0 had when the parent was snapshotted. Linux gives new tap devices random MACs, so a fork's gateway would have a different MAC and the guest would send frames to a MAC that doesn't exist until its ARP entry expires. Pinning tap0 to 06:00:ac:10:00:01 in every namespace makes forks online instantly. This was found in the spike.
  • tap0 is owned by the VM's uid (ip tuntap add … user 1000NN), because Firecracker opens it after dropping root.
  • Why dune's own chains. Docker on midas sets the FORWARD policy to DROP. dune inserts a jump to DUNE-FORWARD at the top of FORWARD, and keeps all its rules in its own chains so it can flush and rebuild them at every start without touching anyone else's.
  • The host veth is named after the VM (dune-<id>), not the slot. Naming by slot once let cleanup of one VM delete another VM's interface after the slot was reused.
  • No inbound connections. There is no port forwarding; the guest is behind two NATs. The host can reach the namespace's 10.200.x address, but not 172.16.0.2. dune reaches into guests through vsock instead (chapter 11).
  • DNS has no kernel boot argument, so image.Prepare writes /etc/resolv.conf (1.1.1.1, 8.8.8.8) into the rootfs at import, replacing systemd-resolved's symlink.
  • Teardown. ip netns delete only unlinks the name; the kernel destroys the namespace asynchronously, once nothing references it. netns.Delete therefore deletes the host veth explicitly first; deleting one end of a pair removes both, synchronously.
On midas
ip netns list                                         # dune-<id> per VM
ip -br addr show | grep dune-                         # host ends of the veths
sudo ip netns exec dune-<id> ip -br addr             # lo, veth0, tap0: the inside
sudo ip netns exec dune-<id> ip -d link show tap0     # "tun type tap … user 1000NN"
sudo ip netns exec dune-<id> iptables -t nat -S       # NAT #1
sudo iptables -S DUNE-FORWARD; sudo iptables -t nat -S DUNE-POSTROUTING   # host rules
dune exec <id> ip neigh                                  # guest's ARP cache: .1 at 06:00:ac:10:00:01
sudo ip netns exec dune-<id> tcpdump -ni tap0 -c 10   # watch guest traffic (if tcpdump installed)
Chapter 11

vsock and the guest agent

dune needs to run commands in guests and open terminals, without SSH and without network access to the guest. It uses vsock, a socket family (AF_VSOCK) designed for host-to-guest communication. Addresses are a context ID (CID) and a port instead of an IP and a port; the guest is CID 3.

Firecracker implements the virtio-vsock device itself, in userspace (there is no vhost_vsock module loaded on midas). On the host side it appears as a unix socket, /v.sock in the jail. To connect to a guest port, the host connects to that socket and speaks a one-line handshake (Backend.DialAgent):

host → firecracker:  CONNECT 1024\n
firecracker → host:  OK <host port>\n     then a raw byte stream to the guest

The agent (cmd/dune-agent) is a static Go binary, so it runs on any guest libc. image.Prepare installs it at import, together with a systemd unit enabled by a symlink in sysinit.target.wants (what systemctl enable would do, done without running systemd). Go's net package doesn't know AF_VSOCK, so the agent creates the socket with raw syscalls and wraps each accepted fd in an *os.File, which Go's runtime poller handles like any socket.

After a restore, Firecracker sends the guest a vsock transport reset: connections that were open at snapshot time are dropped. The agent's listening socket survives, because it's just state in guest memory. fixup retries for up to 3 seconds to cover the moment of the reset.

The PTY endpoint opens /dev/ptmx, unlocks and names the slave (TIOCSPTLCK, TIOCGPTN), and starts a login shell with the slave as its controlling terminal in a new session. That gives job control and Ctrl-C the way a real terminal does.

Chapter 12

Processes, systemd and the API

Why VMs survive a daemon restart

systemd tracks a service by its cgroup: every process duned starts lands in duned.service's cgroup, and stopping or restarting the service kills everything in it (KillMode=control-group, the default). VMs started as plain children would die with every systemctl restart duned.

So duned launches each jailer through systemd-run --scope --unit=dune-vm-<id>.scope --slice=dune.slice. systemd creates a transient scope unit, moves the systemd-run process into its own cgroup, and systemd-run then execs the jailer, which execs Firecracker. One pid all the way down, so the pid duned records stays the VM's pid. The VM now belongs to the scope, not to duned. It also gets setsid() so a Ctrl-C in a terminal running duned can't signal it.

After a restart, duned is no longer the VMs' parent. Manager.Recover checks each recorded pid by reading /proc/<pid>/cmdline for --id <vm> (Firecracker keeps the jailer's arguments), which guards against a recycled pid belonging to something else.

How a request reaches a VM

  1. dune fork … on your Mac sends HTTP to 100.97.247.80:7070. Tailscale carries it inside WireGuard, so it's encrypted and authenticated to your device.
  2. WhoisAuth asks tailscale whois which tailnet login owns the source IP, and rejects anyone not in allow_users. An empty list rejects everyone.
  3. BrowserGuard defends against attacks through your own browser: the Host header must be one of midas's names (stops DNS rebinding), and non-GET requests need the X-Dune-Request header, which a foreign website can't add without a CORS preflight duned never approves (stops CSRF). WebSocket upgrades check Origin.
  4. The handler calls the Manager, which takes a per-VM or per-snapshot lock, updates SQLite, and calls the backend.
  5. The backend speaks HTTP to Firecracker over jail/…/root/run/api.sock, and HTTP to the agent over jail/…/root/v.sock.

On midas itself, the unix socket /run/dune/duned.sock (mode 0600, root only) skips the Tailscale checks: filesystem permissions are the authentication.

On midas
systemctl status duned

cat /sys/fs/cgroup/dune.slice/dune-vm-<id>.scope/memory.current

Chapter 13

What is not isolated yet

Being able to explain the isolation includes knowing where it stops. As of this writing:

  • No resource limits. The scopes give accounting, not limits: no MemoryMax, no CPUQuota. A guest is bounded by its configured vCPUs and RAM, but Firecracker's own overhead and disk I/O aren't capped, and nothing stops the host from being overcommitted by many VMs.
  • Guests have outbound internet. Anything a guest runs can reach the internet as midas (and anything on midas's LAN). Only VM-to-VM forwarding is dropped.
  • No PID or user namespace. The jailer can create a PID namespace (--new-pid-ns); dune doesn't use it, so a compromised Firecracker can see host process lists. Its uid can't signal them, but it can read /proc details that a namespace would hide.
  • Shared host kernel. KVM, netfilter, XFS and the page cache are shared by every VM. A host kernel bug reachable from a guest affects all of them; that's true of every KVM-based system.
  • Forks share secrets. Anything in the parent's memory or disk at snapshot time (keys, tokens, machine-id) is in every fork.
  • duned is root and holds everything. Its API is the real security boundary for the host: the Tailscale allow list, the Host/CSRF guard, and the 0600 unix socket.

Glossary

KVM
Linux's hypervisor module. Turns the CPU's virtualization extensions into an ioctl API on /dev/kvm.
VMM
Virtual machine monitor: the userspace program that drives KVM and emulates devices. Firecracker here; QEMU elsewhere.
VM exit
The CPU leaving guest mode to let the host handle something (a device access, an interrupt).
NPT / EPT

memslot
A KVM mapping from a range of guest-physical memory to a range of the VMM's virtual memory.
virtio-mmio
Paravirtual devices (the guest knows it is virtual) discovered at fixed memory addresses rather than over PCI.
jailer
Firecracker's launcher: builds the chroot, enters namespaces, drops privileges, execs Firecracker.
pivot_root
Swaps a mount namespace's root filesystem. Stronger than chroot(), which leaves the old root reachable.
seccomp
A per-thread kernel filter that kills or rejects syscalls not on an allowlist.
namespace
A per-process view of one kernel resource: mounts, network, pids, users, and more.
cgroup
A kernel group of processes for accounting and limits. systemd units are cgroups.
scope
A systemd unit for processes started elsewhere and handed to systemd, as opposed to a service, which systemd starts itself.
loop device
A block device backed by a file.
sparse file
A file with holes: ranges that occupy no disk space and read as zeros.
discard / fstrim
Telling the layer below which blocks are free. On a loop device that becomes punching holes in the file.
extent
A contiguous run of file data, mapped to a contiguous run of disk blocks.
reflink
A file copy that shares the source's extents, with copy-on-write. The FICLONE ioctl.
hard link
A second name for the same inode. No copy, no copy-on-write.
page cache
The kernel's in-RAM cache of file contents, shared by every process that maps or reads the file.
MAP_PRIVATE
An mmap flag: reads share the file's pages, writes go to private copies.
RSS / PSS
Resident set size counts every page a process maps; proportional set size divides each shared page among the processes sharing it.
dirty log
KVM's bitmap of guest pages written since it was last read. The basis of diff snapshots.
head
dune's name for a VM's latest snapshot, which its next diff snapshot builds on.
tap / veth
A virtual NIC wired to a file descriptor / a pair of virtual NICs wired to each other.
MASQUERADE
Source NAT to the outgoing interface's address, with conntrack reversing it for replies.
vsock
A socket family for host-to-guest streams, addressed by CID and port.
slot
dune's per-VM integer, unique among live VMs. Determines the uid and the host-side /30.
